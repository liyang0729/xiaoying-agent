# 01 需求分析

## 用户与目标

用户是企业员工，需要就公司制度（报销、请假、采购等）或产品问题获得**可靠**的答案。
"可靠"在此项目中被具体化为：

1. 回答必须基于检索到的文档原文，并给出文档 ID 与原文片段（可溯源）；
2. 资料不足或互相矛盾时，如实说明缺口/冲突并追问，**不得编造或擅自取舍**；
3. 工具失败时不崩溃，能调整动作或如实报告。

## 输入与材料

- 用户问题，及可选的对话历史（支持上下文追问）；
- 合成知识库 `data/knowledge_base.json`：7 篇制度文档，每篇含文档 ID、标题、版本日期、正文。
  其中 D01（30 天）与 D02（15 天）对报销时限的规定互相冲突，且均未写明适用范围与优先级，
  该冲突**故意不加消解**，用于驱动"冲突处理"验收场景。

## 范围

- 运行方式：CLI（单次提问 + 多轮对话两种模式）；
- 模型：任意 OpenAI 兼容接口（经 `.env` 配置），另提供离线 Mock 模式；
- 非目标：Web 界面、线上部署、多 Agent 协作、向量检索（理由见 02）。

## 实际投入与未完成部分（按考核要求如实记录）

- 实际用时：约 2 小时（含设计、实现、场景测试、文档撰写与调试；
  其中一次接口不一致 bug 的定位与修复约 10 分钟）；
- 未完成部分：docs/02"生产化差距"一节中的章节切分检索与向量检索
  仅以文字形式讨论演进方向，未实际实现（理由：合成语料仅 7 篇，
  关键词检索已覆盖改写问法验收点，投入产出不划算）；
  权限过滤、会话历史落盘同样未实现，见 docs/05 下一步改进。

## 成功标准（对齐题目的必验收点）

| 验收点 | 成功标准 | 对应示例 |
|---|---|---|
| 明确答案 | 回答含引用 ID 与原文片段，且片段确能支持结论 | examples/01 |
| 文档冲突 | 列出冲突双方及引用，追问适用制度，不擅自选择 | examples/02、03 |
| 资料外问题 | 说明检索无结果与资料缺口，不编造 | examples/04 |
| 改写后的相似问题 | 换措辞的查询仍能命中目标文档 | examples/03 |
| 上下文追问 | 多轮模式下后续问题能结合历史理解 | examples/05 |
| 工具失败 | 错误喂回模型，模型调整动作或如实报告 | examples/06 |
| 步数上限 | 达到上限返回明确 unfinished 状态 | examples/07 |
