# 02 方案设计

## 总体架构

原生实现（不使用 Agent 框架），分三层：

```
src/cli.py    交互层：命令行入口、trace 展示、多轮历史维护
src/agent.py  决策层：ReAct 循环、输出解析、步数上限、trace 记录
src/llm.py    模型层：OpenAI 兼容调用 + MockLLM（接口一致，可互换）
src/tools.py  工具层：search / read_doc 两个业务工具
```

分层的动机：决策逻辑不感知"模型怎么调""数据在哪"，换模型厂商或换存储
只需改动对应层；测试时可用 MockLLM/临时数据替换任意一层。

## 调用流程（动态决策循环）

每轮执行：

1. 模型看到完整对话历史（system 规则 + 历史 + 本轮问题 + 历步观察结果）；
2. 模型输出**恰好一个** JSON：`{"thought", "action", "args"}`；
3. 按动作分流：
   - `search` / `read_doc` → 执行工具，把结果（或错误信息）格式化为
     observation，以 user 消息追加回对话，回到 1；
   - `ask_user` → 返回 `need_user_input`；
   - `finish` → 返回 `answered`，透出 answer / citations / gaps；
4. 循环受 `max_steps`（默认 8）约束，走满仍未结束返回 `unfinished`。

"下一步做什么"完全由模型在每轮根据最新观察结果决定，代码中没有
预设的分支流程或自动重试；解析失败、工具失败均以统一格式的观察结果
喂回模型，由模型自行调整（纠错也消耗步数，故不会无限循环）。

## 动态决策的关键设计

- **两层信息**：search 只返回片段（正文前 80 字），read_doc 才有全文。
  片段不够用时模型有真实动机读取原文（examples/01 的 step 2 决策依据
  "摘要片段被截断，需读取全文"即为实录）；
- **冲突规则写进 system prompt**：要求列出冲突双方及引用并 ask_user，
  不得擅自选边（examples/02、03）；
- **观察结果以 user 角色喂回**：OpenAI 兼容接口无统一的工具结果角色，
  以文本形式追加是最可移植的做法。

## 技术取舍

| 选择 | 理由 |
|---|---|
| 原生实现，不用 LangGraph/ADK 等 | 需求只有一个循环 + 两个工具，原生约 300 行可完全掌控；框架引入的抽象层对本题无增益，且框架名不构成评分项 |
| 关键词 + 同义词表检索，不用 embedding | 语料仅 7 篇合成文档，关键词打分（标题 3 分/正文 1 分）即可满足"改写问法"验收；完全可解释、零额外依赖。若语料增大，可升级为 BM25 或向量检索，接口 `search(query)` 不变 |
| JSON 动作而非 function calling | OpenAI function calling 在各兼容厂商的兼容度不一；纯文本 JSON + 严格校验 + 错误喂回的方式在任何 OpenAI 兼容服务上都可运行，且解析失败本身构成一条可观察的决策路径 |
| temperature=0 | Agent 需要稳定可复现的工具决策，评审可能重复运行对比 |

## 步数上限

默认 8，CLI `--max-steps` 可覆盖。达到上限返回
`{"status": "unfinished", "gaps": "达到最大步数 N，任务未完成"}`，
examples/07 为 `--max-steps 1` 的实录。

## 安全与 Harness

模型输出的每一步都经过确定性代码的约束与校验，不依赖模型自觉：

| 机制 | 位置 | 防什么 |
|---|---|---|
| 动作白名单 + schema 校验 | `agent.parse_action` | 模型/注入内容诱导出的任何非法动作（未知工具、非 dict 参数）都被拒绝并喂回纠错；系统不存在 shell/写文件/网络类高危工具，能力天然收敛 |
| 数据/指令通道分离 | observation 以 `<observation>` 标签包裹 + system 规则 7 | 间接提示注入：文档内容或工具结果中嵌入的"指令"被视为数据；用户问题中试图修改规则的请求同样不予理会 |
| 引用校验闸门 | `agent.verify_citations`，finish 前强制执行 | 幻觉引用/被诱导的错误引用：doc_id 必须存在、quote 必须是原文的连续片段（空白归一化后比对）；不实引用被拒绝并喂回模型修正，修正也消耗步数 |
| 步数上限 | `run_agent(max_steps)` | 无限循环、纠错风暴、被诱导的消耗性行为，达到上限返回明确 unfinished |
| 失败即观察 | 工具异常/解析失败统一包装为结构化观察结果 | 故障不外泄执行流，同时构成模型调整动作的输入 |

已知残留风险：规则 7 属于提示层防御，无法保证对抗一切注入变体；
生产化场景应在检索层增加内容安全扫描（见下文"生产化差距"）。

## 生产化差距（与真实业务知识库的对比）

当前 `data/knowledge_base.json` 是按题目要求的理想化合成材料
（自带 doc_id / 版本日期 / 干净字段）。真实企业知识库与之的主要差距
及对应演进方向：

| 真实场景问题 | 当前实现 | 生产化方向 |
|---|---|---|
| 文档来源为 Word/PDF/Confluence，格式杂乱 | 直接使用结构化 JSON | 增加文档解析与清洗层，解析产物仍归一为结构化条目，下游不变 |
| 制度文档动辄数十页 | 检索/引用粒度均为整篇文档 | 按标题层级切分为章节片段，检索与引用都以片段为单位（检索粒度 ≠ 文档粒度），引用时回溯所属文档 ID |
| 语义改写幅度大，关键词召回有边界 | 同义词表 + 关键词打分 | BM25 或向量检索（embedding + FAISS 等），可叠加 rerank；`search(query)` 接口不变，仅替换实现 |
| 冲突消解依赖元数据（适用范围/生效日期/废止标记） | 元数据缺失时由模型兜底：列冲突并 ask_user | 数据治理补齐元数据后，检索层按元数据过滤即可在源头消解大部分冲突；模型追问只是元数据缺失时的防御机制，而非治本手段 |
| 制度有权限可见范围 | 无权限概念 | 检索层增加按用户身份的可见性过滤，确保 Agent 引用的文档用户本就有权阅读 |

本项目的分层设计使上述升级大多只影响 `tools.py` 内部实现：
`agent.py` 依赖的仅是"工具名 + 参数 + JSON 结果"这一约定接口。
