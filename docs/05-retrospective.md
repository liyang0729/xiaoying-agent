# 05 复盘

## 最难的问题

**"固定流程"与"模型决策"的边界。** 最初容易把冲突处理写成
"search 结果里同时出现 30 和 15 就追问"的 if-else——但这正是题目明文
排除的做法。最终把业务规则（冲突必须追问、不得选边）从代码里挪进
system prompt，由模型在每轮决策时遵守；代码只负责机械地执行模型
选择的动作、可靠地喂回观察结果。这个拆分想清楚后，整个 agent.py
反而变得很短。

**失败信息的统一格式。** 工具失败最初想用"重试三次"，但那是固定重试，
不构成决策。改为把 `{"error": ...}` 作为与成功结果同构的观察结果喂回，
让模型自己决定换查询、换工具还是如实报告——examples/06 中模型
"读取失败后改用 search 交叉验证"的路径即是该设计的产物。

## 学习收获

1. ReAct 循环的本质是"把每次工具结果变成模型下一轮的输入"，
   终止条件（finish/ask_user/步数上限）与纠错通路（喂回错误）都要在
   循环结构里显式设计；
2. 测试分两层写：机制层用 Mock 剧本确定性验证（流程、上限、失败处理），
   效果层用真实模型运行记录证明决策质量——两者的证明力不同，须分开陈述；
3. prompt 中的业务规则要写成可执行的指令（"列出冲突双方及引用，
   用 ask_user 确认"），而不是态度性描述（"请谨慎回答"）。

## 下一步改进

1. **检索升级**：引入 BM25 或轻量 embedding，并加一层"检索无结果时的
   查询改写"，缓解关键词召回边界问题；
2. **文档优先级元数据**：给文档增加"适用范围/生效日期/是否废止"字段，
   让模型可依据元数据消解部分冲突，而不是一律追问；
3. **结构化会话存储**：多轮历史目前只在内存中，可落盘以支持跨会话追问；
4. **评估自动化**：把 7 个验收场景做成可重复执行的回归脚本，
   每次改动 prompt 后自动对比结果。
